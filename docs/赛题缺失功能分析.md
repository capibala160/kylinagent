> 基于第十四届中国软件杯 A2 赛题《基于操作系统安全审计多维 Agent 的设计与实现》

---

## 一、项目优势（已实现的亮点）

| 维度 | 实现情况 | 评价 |
|------|---------|------|
| OS 多维感知 | ✅ 6大类 25+ 个工具 | system/process/network/disk/file/service/diagnose 覆盖 lsof/ss/netstat/journalctl/ps/df 等 |

## 二、核心缺失功能（按赛题要求逐项对照）

### 2.1 🔴 MCP 标准协议未真正实现（最高优先级）

**赛题要求**："通过实现 MCP(Model Context Protocol) 协议，将大模型感知系统实时状态..."

**现状问题**：
- `schema.py` 中虽然定义了 `MCPRequest`/`MCPResponse`/`InitializeResult` 等数据结构，但 **API 路由中完全没有实现 MCP 标准端点**
- 当前 `/api/tools` 返回的是自定义格式，不是 MCP 标准的 `tools/list` JSON-RPC 响应
- 缺少以下 MCP 核心端点：
  - `POST /mcp/initialize` —— 协议握手
  - `POST /mcp/tools/list` —— 标准工具列表
  - `POST /mcp/tools/call` —— 标准工具调用
  - JSON-RPC 2.0 请求/响应格式
- 当前 LLM 与工具的交互是**直接函数调用**（`tool.safe_execute()`），不是通过 MCP 协议通信

**影响**：赛题评分中 "OS 感知 MCP 工具实现" 占 55% 中的核心部分，若 MCP 只是"伪实现"会大幅扣分。

**建议**：在 `routes.py` 中新增 `/mcp` 路由组，实现标准 MCP Server 端点，让 LLM 通过 MCP 协议调用工具。

---

### 2.2 🔴 缺少"操作类"工具（清理/删除/修改）

**赛题要求**："帮我清理系统日志"——Agent 感知日志占用空间，执行删除前触发安全校验，判断是否为关键数据库日志、权限是否合规。

**现状问题**：
- 现有 25+ 工具**全部是信息查询类**（read-only），没有任何真正的"修改系统状态"的操作工具
- 缺少：
  - `clean_logs` —— 安全清理日志（带路径白名单、大小阈值）
  - `safe_remove` —— 安全删除文件（先检查是否为关键文件）
  - `restart_service` / `start_service` / `stop_service` —— 服务管理
  - `truncate_file` —— 清空/截断文件（如日志轮转）
  - `create_user` / `modify_user` —— 用户管理（最小权限下）
- `kill_process` 虽然有，但属于特例

**影响**：赛题场景明确要求"清理系统日志"，当前项目只能"查看"不能"清理"。

**建议**：新增 5-8 个操作类工具，每个都必须经过安全校验 + 二次确认 + 最小权限执行。

---

### 2.3 🟡 安全意图校验未结合 LLM（仅正则匹配）

**赛题要求**："结合意图识别模型/规则，将 LLM 生成的原始指令经过'安全审计'标识风险"

**现状问题**：
- `validate_intent()` 只是**纯正则匹配**提示词注入（20+ 条正则），没有任何 LLM 参与
- `INTENT_ANALYSIS_PROMPT` 和 `SECURITY_REVIEW_PROMPT` 在 `prompts.py` 中定义了，但**代码中从未被调用**
- 没有利用 LLM 对自然语言进行深度语义分析（如理解"帮我清理系统日志"中的"清理"是安全操作还是误操作）
- 没有"意图分类 → 风险预判 → 操作建议"的 LLM 增强流程

**影响**：自然语言对话准确率评分可能受影响，安全审计的深度不足。

**建议**：在 `agent/core.py` 的 INTENT_RECEIVED 阶段后，增加 LLM 意图分析调用，生成意图分类和风险预判。

---

### 2.4 🟡 缺少 root 权限申请/审批机制

**赛题要求**："日常多维审计使用受限的 Account 执行，必要时申请 root"

**现状问题**：
- `PrivilegeExecutor` 支持受限用户执行，但**没有"申请 root → 审批 → 临时提权"的闭环机制**
- 当命令需要 root 才能执行时，要么直接失败，要么降级为当前用户执行
- 没有记录"权限提升"的专门审计节点
- 前端没有权限申请的 UI 流程

**影响**：最小权限代理执行的完整性不足，赛题明确要求"必要时申请 root"。

**建议**：
1. 在 `PrivilegeExecutor` 中增加 `request_root_elevation()` 方法
2. 当检测到需要 root 的命令时，返回"需要 root 权限"状态给前端
3. 前端弹出"权限申请"对话框，用户输入理由后确认
4. 通过 sudo 临时提权执行，并记录专门的 `PRIVILEGE_ELEVATION` 审计节点

---

### 2.5 🟡 审计日志的异常回溯与统计分析缺失

**赛题要求**："完整记录...的闭环日志，支持异常回溯"

**现状问题**：
- ✅ 有单条链路记录和查询
- ❌ 没有**异常模式自动检测**（如检测到多次拦截/失败时自动告警）
- ❌ 没有**审计日志统计分析**（每日拦截次数、高频风险命令、用户行为画像）
- ❌ 没有**审计日志导出**功能（CSV/JSON 导出）
- ❌ 虽然配置了 `retention_days: 90`，但**没有自动清理过期日志的实现**
- ❌ `AuditLogger.query_chains()` 是线性扫描 JSONL 文件，数据量大了性能差

**建议**：
1. 增加 `audit/stats` API，返回拦截率、高频命令等统计
2. 增加 `audit/export` API
3. 增加定时任务清理过期日志
4. 考虑将审计关键字段同步到 SQLite 数据库索引

---

### 2.6 🟡 前端缺少系统监控仪表盘

**赛题要求**："B/S 架构"，运维场景需要直观的监控展示。

**现状问题**：
- 前端只有对话界面、审计日志、工具列表、配置展示
- ❌ 没有独立的**系统状态监控仪表盘**（Dashboard）
- ❌ 没有**可视化图表**（CPU/内存/磁盘趋势图、网络流量图）
- ❌ 所有数据都是文本输出，没有 ECharts/Chart.js 等图表
- 虽然有 `get_system_info` 等工具，但结果只在对话中展示

**建议**：新增一个"系统监控"视图，使用 ECharts 展示：
- CPU/内存/磁盘实时使用率
- 网络连接状态图
- 最近 24 小时审计事件趋势
- 服务健康状态面板

---

### 2.7 🟡 聊天记录未持久化

**现状问题**：
- `SessionManager` 使用内存字典存储会话，**重启后丢失**
- `SessionState.message_history` 没有写入数据库
- 虽然 `db.py` 有 UserModel 和 SessionModel，但 SessionModel 只存了 sid/username/时间，没有存聊天记录

**建议**：在 SQLite 中新增 `chat_messages` 表，实现聊天记录持久化。

---

### 2.8 🟡 SSE/流式响应未接入主流程

**现状问题**：
- `llm/client.py` 有 `chat_completion_stream()` 方法
- 但 `api/routes.py` 的 `/chat` 接口**没有 SSE 端点**
- 前端 `app.js` 也没有使用 EventSource
- 当前响应是"等待所有工具执行完成后再一次性返回"，用户体验较差（尤其是 LLM 推理慢时）

**建议**：新增 `/chat/stream` SSE 端点，让 LLM 推理过程和工具执行结果可以流式推送给前端。

## 三、代码层面的具体问题

### 3.1 HIGH 级别操作被直接阻断，而非二次确认

**位置**：`security/guard.py` 第 118-119 行

```python
if risk_level == RiskLevel.HIGH:
    return False, f"检测到高危操作..."  # 直接 block
```

**问题**：赛题中 `kill -9` 和 `systemctl stop/restart` 属于"需要二次确认"的操作，但当前代码中 HIGH 被直接阻断，不会进入 `needs_confirm` 流程。

**建议**：HIGH 级别应返回 `action="confirm"`，允许用户二次确认后执行。

### 3.2 白名单配置未生效

**位置**：`security/rules.py` 第 191-203 行

**问题**：`CommandWhitelist` 的 `allowed_prefixes` 是**硬编码**的，没有从 `agent.yaml` 的 `security.allowed_command_prefixes` 加载。而且配置文件中该字段是字符串列表（如 `"ps, top, htop..."`），但代码期望的是单独的前缀列表。

### 3.3 白名单检查永远不会触发

**位置**：`security/guard.py` 第 122-128 行

```python
if tool_name is None or tool_name in ["execute_shell", "run_command"]:
    if not self.whitelist.is_allowed(command):
        ...
```

**问题**：项目中**没有 `execute_shell` 或 `run_command` 工具**，所有命令都是通过专门的 Tool 类执行的。因此 `tool_name` 永远不会是 None 或这两个值，白名单检查永远不会触发。

**建议**：为每个高危操作类工具增加白名单检查，或者增加一个通用的 `execute_shell` 工具（带严格限制）。

### 3.4 安全规则正则与工具调用格式不匹配

**位置**：`agent/core.py` 第 186 行

```python
cmd_str = f"{tool_name}({json.dumps(arguments)})"
```

**问题**：`validate_command()` 接收的 `cmd_str` 格式是 `read_file({"path": "/etc/passwd"})`，但规则引擎中的正则（如 `r"rm\s+.*-rf"`）不会匹配这种格式。因此工具调用的安全校验实际上主要依赖 `tool_name` 判断，而不是参数内容。

**建议**：为每个工具增加参数级别的安全检查（如 `read_file` 检查 path 是否在敏感路径列表中）。

### 3.5 `psutil` 安装了但从未使用

**位置**：`requirements.txt` 第 6 行

**问题**：`psutil==5.9.8` 在依赖中，但代码中所有系统信息都通过 `subprocess` 调用命令获取，没有使用 `psutil`。`psutil` 可以提供更稳定、跨平台的系统信息获取，且无需 shell 调用。

**建议**：用 `psutil` 替代部分 `subprocess` 调用（如进程列表、CPU/内存信息），提高稳定性和性能。

### 3.6 `CORS` 配置允许方法缺失 PUT/PATCH/DELETE 实际使用

**位置**：`main.py` 第 41 行

```python
allow_methods=["GET", "POST", "DELETE"]
```

**问题**：当前没有使用 PUT/PATCH，但 `DELETE /session/{session_id}` 已使用，暂时无影响。

## 五、改进优先级建议

1. **实现 MCP 标准协议端点**（`/mcp/initialize`, `/mcp/tools/list`, `/mcp/tools/call`）
2. **新增操作类工具**（`clean_logs`, `safe_remove`, `restart_service` 等），覆盖赛题"清理日志"场景
3. **修复 HIGH 级别阻断逻辑**，改为二次确认而非直接阻断
4. **制作作品提交文档**（需求规格说明书、系统设计说明书、测试报告、PPT、演示视频）

### P1（显著提升评分竞争力）
5. **LLM 增强意图分析**：在 `agent/core.py` 中调用 `INTENT_ANALYSIS_PROMPT`，让 LLM 参与意图理解和风险预判
6. **root 权限申请机制**：实现"申请 → 审批 → 临时提权 → 审计记录"闭环
7. **前端监控仪表盘**：新增 Dashboard 视图，用 ECharts 展示系统状态图表
8. **审计日志统计分析**：新增 `/api/audit/stats` 和 `/api/audit/export` 接口

### P2（锦上添花，完善体验）
9. 聊天记录持久化到 SQLite
10. SSE 流式响应 `/chat/stream`
11. 使用 `psutil` 替代部分 `subprocess` 调用
12. 审计日志自动清理过期文件
13. 修复白名单配置加载问题
14. 为每个工具增加参数级安全检查
